# Persisted knowledge scope bindings (U03h)

Migration 2 adds `mf_knowledge.scope_bindings` with a composite `(principal, display_graph_id)` primary key, a unique `group_id`, and a foreign key to the existing canonical `scopes` table. The principal identifier uses the command dispatcher’s nonblank, 1–128 character printable ASCII domain. The display graph ID uses the backend reader’s 1–128 ASCII letter, digit, underscore, and hyphen domain. Both identity columns use `C` collation for exact, case-sensitive keys. The database enforces these domains and stores only the mapping and creation time; canonical scope JSON remains in `scopes`. The unique group key also indexes the foreign key lookup. It allows one owner/name for a complete logical scope in this slice and reserves a binding after tombstoning.

`migrate(connection)` remains explicit and migration-owner supplied. It takes a transaction-level advisory lock, sets a catalog-only search path and bounded statement/lock timeouts, validates contiguous known migration versions and every applied SQL checksum, then checks the current catalog shape against the latest applied shape fingerprint. A v1 database is checked against its v1 fingerprint before migration 2. Each pending migration and its resulting fingerprint are written atomically; a fresh install applies both in one transaction. Existing migration 1 SQL and records are left intact. Drift, gaps, unknown future versions, and checksum errors fail closed; there is no downgrade or automatic runtime migration.

`ScopeBindingStore.bind` is a trusted-host provisioning operation. It validates identity and a copied `KnowledgeScope` before opening a connection, registers and locks the authoritative canonical scope through the ledger helper, and inserts a mapping only when neither the composite key nor group is owned by a different tuple. An identical bind is idempotent and keeps its original creation time. A conflicting bind rolls back its newly inserted scope and raises fixed `Conflict`; there is no update, transfer, delete, or alias path.

`resolve` looks up only the exact principal/display ID pair, joins the stored canonical scope, revalidates its full v1 shape and computed group ID, and rejects tombstones. It returns a frozen `BindingRecord`. This is identity lookup, separate from actual host authentication and authorization. The host must supply an authenticated principal; a caller-supplied public field is insufficient. Resolving a binding is also separate from read admission while a write is active. A read barrier, organization roles, route wiring, and cross-page consistency remain outside this slice. Transactions end before any future provider call.
