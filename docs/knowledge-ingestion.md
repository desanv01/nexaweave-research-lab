# Ledger-backed knowledge ingestion (U03b foundation)

`KnowledgeIngestionCoordinator` is an internal boundary in the isolated knowledge package. Its caller supplies an already authorized scope, validated source and ontology, an injected persistent `Ledger`, an injected provider, and a finite timeout. It neither initializes Graphiti nor creates credentials, migrations, or a network service. The old direct provider remains a compatibility spike; application routing through this coordinator is future work.

The coordinator revalidates copied DTOs, source hash and ontology revision and rejects duplicate evidence IDs before database access. It uses the ledger's canonical request fingerprint. It admits the immutable operation, claims one scope write slot, then dispatches Graphiti only after the claim transaction commits. A completed duplicate returns the stored metadata receipt without Graphiti work. Running and uncertain operations remain quarantined; busy and conflicting operations are not retried internally.

After dispatch, it checks the episode ID and every returned fact's scope, episode link and source evidence. `completion_proof` then reads the episode and completion marker with fixed parameterized Cypher. It requires the exact scope, fingerprint, source content and hashes, complete marker, and ordered source evidence IDs. This method never calls extraction or model APIs. Only a matching active attempt is acknowledged in PostgreSQL with a bounded `CompletionReceipt`; Graphiti facts and prompt content are not stored in the ledger. The same monotonic deadline covers provider dispatch and proof. It is rechecked after each await because a provider can suppress cancellation and return late. Short bounded ledger acknowledgment and uncertainty recording may extend total wall time.

Provider exceptions, validation failures, timeouts, cancellation, and ambiguous acknowledgment are treated as uncertain after dispatch starts. The coordinator makes a bounded shielded attempt to record uncertainty. If that fails, the running ledger admission still blocks replay. Offloaded synchronous database work holds a bounded permit until its underlying thread finishes, even if the awaiting coroutine is cancelled. A cancelled claim is observed by a background cleanup task that records uncertainty if the claim committed. Process death can interrupt that cleanup; the committed running admission remains quarantined. The connection factory must impose a finite connect timeout; threads cannot be forcibly stopped by asyncio cancellation.

This is not a distributed exactly-once guarantee. A token cannot fence a stale Neo4j writer, and asyncio cannot forcibly terminate a noncooperative provider. Proof here is only for active attempt completion; an uncertain attempt requires a separate reviewed reconciliation API. There is no automatic extraction retry, heartbeat expiry release, marker-absence retry, usage reservation, tenant authorization, Flask cutover, durable fact storage, or public deployment in this slice.

Pure fixtures cover validation, duplicate handling, proof mismatch, timeout, late proof after suppressed cancellation, cancellation, and ambiguous storage. Opt-in PostgreSQL fixtures reuse the accepted loopback disposable database guard and inspect real admissions and lock availability during a synthetic provider wait. They also inject a lost acknowledgment after a real completion commit, then read the stored receipt through a fresh coordinator without redispatch. A fresh coordinator object is tested; this is not an OS-process restart test. The Neo4j proof fixture uses synthetic local model collaborators only. Main owns execution and further live-provider, crash, process-restart, and reconciliation qualification.
